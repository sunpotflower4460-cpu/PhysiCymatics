# M6-2 休止・イベント駆動の実装結果

設計の根拠は `docs/m6_2_event_driven_design.md`。本書は実装と実測の記録。

## 実装した休止方式

- 物理状態（FLYING / SITTING / LOST）と計算管理状態（通常走査 / 休止）を分離。
  休止は新しい物理状態ではなく「その区間は状態変化が起きないと判定できた」
  という管理情報（`sleeping` + `wakeT` + `sleepT0`）。
- 着座休止: モードエネルギーの増加上限 `dE/dt <= |f|` から未来の加速度下限
  `g - Σ(F_j + ω_j(1+2ζ)(E_j+F_jΔ))|Φ_j|` を求め、安全余裕（0.25 m/s²）を
  引いても正である期間だけ休止する。
- 飛行休止: 板高さの上限 `Σ(E_j+F_jΔ)/ω_j` と放物線の最小値から
  「それ以前には接触しない」下限時刻を求める。板外到達時刻（直線と円の交点）
  も起床候補に入れる。下限到達後は M6-1 の接触探索へ戻る。
- 短すぎる休止（8ステップ以下）は管理コストの方が高いため採用しない。
  休止判定に失敗した粒子は16ステップ再判定を空ける（管理のみの最適化）。
- 周波数・score・駆動点の変更時は全休止を無効化（状態は現在時刻へ復元して保持）。
- 休止あり/なしは切替可能（`sleep_enabled` / `{enabled}`）。基準経路は残してある。

## 休止あり/なしの一致（検証）

- TS・Python の両方で、同一初期条件の on/off 比較を実施。
  位置の最大差 1e-6 m 未満、衝突・離脱回数と残存数が一致（テストで固定）。
- 周波数 70 / 152 / 173.31 / 368.6 / 649 Hz のサンプルでも一致。
  （20Hz・1240Hz付近・2000Hz は入力経路のみで、モード打切りの物理精度は
  従来どおり未検証として区別する。）
- Python/Web 照合（M6 fixture）も休止あり同士で 1e-6 m 未満・回数一致。

## 実測（TS・Node、152Hz較正力、0.2秒）

| 粒子数 | 休止なし | 休止あり | 省略した粒子更新 | 休止率 |
|---|---|---|---|---|
| 500 | 1396ms | 927ms | 378,951 | 65% |
| 5,000 | 11,923ms | 8,812ms | 3,873,953 | 63% |

弱い駆動（力×0.02、2,000粒、0.5秒）: 11,519ms → 1,855ms（約6倍、休止率99%）。
弱い駆動100,000粒・0.1秒（休止あり）: 82.9秒（休止率100%でも判定・起床処理が残る）。

正直な読み方: 強い駆動では起床・再判定の管理コストが大きく、改善は約1.3〜1.5倍。
着座が支配的な条件では大きな効果がある。60万粒リアルタイムの保証にはならない。

## 空間的な計算共有（M6-2E）について

今回は粒子ごとの `Φ_j(x,y)` 評価を休止判定でのみ使い、領域分割による
共有は未実装。理由: 休止判定の正確さをまず粒子単位で固定するため。
領域上限（領域内全粒子に安全な bound）への拡張は M6-3 の候補。

## スマートフォンへの適性

- 粒子状態は連続配列のまま。休止管理も TypedArray 3本のみ追加。
- snapshot は休止飛行粒子の位置を解析式で復元するため転送量は不変。
  （休止粒子を送らない最適化は未実装。）
- GPU不要の経路を維持。

## 未解決の限界

- 休止 bound はモード ODE の厳密解に対する上限であり、RK4+Hermite の
  数値誤差は安全余裕で吸収する前提（経験的に on/off 一致で検証）。
- サンプル間で完結する浅い接触の見逃し（M6-1 の床）は休止でも増やしていない
  （下限到達後に通常探索へ戻るため）。ただし完全検出ではない。
- c_roll>0 や粒子間衝突を入れた場合、現在の休止条件は無条件には使えない。
- Python 参照の休止は照合用であり、速度は依然として遅い。
