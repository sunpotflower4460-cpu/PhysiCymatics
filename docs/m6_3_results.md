# M6-3 イベントスケジューラ・領域共有・描画転送最適化の結果（M6-3R 監査済み）

設計の前提は `docs/m6_2_event_driven_design.md`（M6-3節）と
`docs/m6_2_results.md`。物理モデルと休止保証は M6-2R から変更していない。
今回変えたのは「どの粒子をいつ触るか」「判定の共有」「表示転送」だけである。
本書は M6-3R の最終監査（境界条件テスト＋反復性能計測）で更新した。

## 実装方式と選定理由

### M6-3A イベントスケジューラ（TypeScript）

- 活動集合: 連続配列 + 位置表による swap-remove 方式。休止・消失した
  粒子はその場で外れ、毎ステップのループは活動粒子だけを回る。
- 起床管理: 起床時刻の最小ヒープ。公称 dt が周波数で変わるため
  「ステップ番号のバケット」ではなく絶対時刻ヒープを選んだ。
  ヒープ項目は取り出し時に `sleeping` と `wakeT` の一致で検証するので、
  無効化（wakeAll）や再予定のあとに残った古い項目では誤起床しない。
- 起床の意味は旧方式と同一: `wakeT <= tNew` の粒子をステップ開始時に
  起こし、ステップ開始時刻へ復元してから通常処理する。休止保証の
  区間を越えて寝かせることはない。
- 粒子ごとの処理本体は旧ループからそのまま切り出した共通関数
  （`advanceParticle`）。旧方式は `{scheduler:false}` で残してある。

### M6-3B 領域単位の計算共有（着座休止の判定のみ）

- 板面を 64×64 の格子に分け、セルごとに全自由度の形状関数 Φ の
  範囲を前計算する。実装されている Φ は「動径ビンの R 値 × 角度の
  三角関数」なので、セルの動径範囲→ビン範囲の R の最小最大、
  角度範囲→三角関数の厳密な範囲（端点＋内部の極値）を組み合わせると、
  セル内の全点で成り立つ範囲が得られる。代表点による近似ではない。
- 先読み（lookahead）の加速度範囲と組み合わせて、セル共通の
  加速度下限（安全側）と、セル内の最良ケース上限（確実に失敗する
  判定の省略用）をキャッシュが変わるたびに1回だけ計算する
  （実測: 全セル再計算でも約 0.8ms、更新は約 0.25 秒に1回）。
- セルで結論が出ない粒子は従来の粒子単位評価へ戻る。
- 飛行休止はもともと Φ を使わず板高さの全体上限で判定しているため
  変更なし。飛行粒子は移動するため、現在セルの範囲で未来全体を
  保証するような使い方はしていない。

### M6-3C 描画転送の差分化

- Worker は毎フレーム全座標を送らず、表示座標が前フレームから
  変わった粒子（番号＋座標）と消失した粒子だけを送る。
  粒子の同一性は状態配列の番号（シミュレーション中は不変）。
- 表示側は座標キャッシュを持ち、差分を適用して描く。物理時刻は
  フレームの時刻そのもので、表示最適化は物理状態に触れない。
- 着座中の粒子は表示座標（x, y）が変わらないため、模様が形成される
  ほど転送量が減る。初回とリセット時は全量を送る。

## 物理的な安全性の根拠（M6-3R 監査を含む）

- スケジューラは処理順序と走査範囲だけを変える。粒子同士は相互作用
  せず板も独立に進むため、粒子ごとの計算結果は順序に依存しない。
  実測でも旧方式と回数・省略回数・起床回数が完全一致し、位置差は
  1e-9 m 未満だった（テストで固定）。
- 監査で追加した境界検証:
  - 活動集合の不変条件（重複登録なし、消失・休止粒子の混入なし、
    swap-remove による処理漏れなし、起床期限超過なし）を
    800ステップ＋周波数変更をまたいで毎ステップ検査。
  - wakeAll 後の古いヒープ項目が何も起こさないこと（旧方式と
    回数・位置が一致）。
  - 消失粒子が活動集合から外れ、二度と活動しないこと。
  - Φ 範囲: 原点を含むセル、角度の折返しセル、動径ビン境界セル、
    外周セルでの決定的格子点検査と、実際の 64×64 全セルの
    サンプル点内包検査。セル下限 ≦ 厳密な下限 ≦ セル上限も
    ランダム 3,000 点で検査。
  - 差分転送: リセット時の全量再送、消失通知がちょうど1回だけ
    であること、再構成座標＝全量 snapshot（毎フレーム）。
- M6-2R の回帰（c_roll>0、70Hz＋649Hz残留、イベント上限、
  微小跳ねの正則化）は既存テストが引き続き合格し、悪化はない。
  M6-1 由来の浅い接触の見逃し可能性と、TS/Python のイベント上限
  の数え方の違いは従来どおりの既知の限界であり、今回の変更では
  触れていない（上限後の区間分割は M6-2R で両言語とも
  「接触を確認しながら進める」形に統一済み。内部反復の安全弁に
  達した場合は最後の接触状態に留まり板面下には行かない）。

## 性能の再測定（M6-3R）

計測環境: Intel Core i9-10910 / 32GB / Node v22.22.2 / vitest。
方法: JIT ウォームアップ後に同一条件（152Hz・seed 7）で
3回反復し、実行順序を回転させ、中央値を取る（大規模は1回）。
前回の単回計測とは絶対値が異なるため、比較は本表内でのみ行う。

| 条件（物理時間） | 休止OFF | M6-2 | M6-3A | M6-3A+B |
|---|---|---|---|---|
| 500粒・強 (1s) | 3.38s | 3.46s | 3.49s | 3.50s |
| 2,000粒・弱 (1s) | 18.06s | 13.82s | 13.62s | 13.45s |
| 5,000粒・強 (0.5s) | 17.02s | 16.75s | 16.89s | 17.36s |
| 5,000粒・弱 (0.5s) | 20.72s | 15.30s | 14.70s | 14.49s |
| 20,000粒・強 (0.2s, 1回) | 27.04s | 26.98s | 26.77s | 26.62s |
| 20,000粒・弱 (0.2s, 1回) | 24.27s | 18.13s | 19.45s | 18.17s |
| 100,000粒・弱 (0.2s, 1回) | 119.24s | 88.95s | 91.24s | 92.61s |

全条件で衝突・離脱・省略・起床・判定の回数は休止方式間で一致
（イベント上限到達は全条件 0 回）。省略した更新は 100,000粒・
0.2秒で約 6,973 万回に達する。RSS の増加は各実行で概ね 20MB 未満
（同一プロセス内の差分値であり絶対値ではない）。

正直な読み方:

- 前回「2,000粒・弱で M6-3 が遅い」と記録した点は、反復計測では
  再現しなかった（M6-2 13.82s に対し M6-3A+B 13.45s）。単回計測の
  ばらつきと実行順序の影響だったと判断する。ヒープ・活動集合の
  管理コストが支配的になる証拠は得られなかった。
- スケジューラ単体の効果は概ね ±3% 以内で、条件によっては
  M6-2 と互角か僅かに遅い。取り除けたのは全粒子走査であり、
  残る支配コストは活動粒子の表面評価である（下記分解）。
- 領域共有は弱駆動で着座判定の約 86% を「確実に失敗」として
  省略し、数% を「確実に成功」で省略した（100,000粒: 成功 44,257 /
  失敗省略 2,441,328 / 全判定 2,789,724）。強駆動では成功はほぼ
  出ず、判定の追加コスト分だけ僅かに遅い場合がある
  （5,000粒・強では交互実行でも中央値で数% の差）。
  表面評価の回数は領域 ON/OFF で完全一致した（33,505,312 回）。

## ボトルネックの分解（実測）

| 処理 | 実測 |
|---|---|
| 板の時間発展のみ | 物理1秒あたり約 0.10 秒 |
| 板表面評価 surfAt の回数 | 2,000粒・強・0.3s で約 836 万回（粒子ステップあたり約 2.1 回）。5,000粒・強・0.5s で約 3,350 万回 |
| 領域キャッシュ全再計算 | 約 0.8ms（先読み更新時のみ、約 0.25 秒に1回） |
| 領域表の初期構築 | 構築時間の差として約 17ms（1回だけ） |
| stats() 作成 | 5,000粒 0.064ms / 100,000粒 0.81ms（全粒子走査×3） |
| snapshot() 作成 | 5,000粒 0.13ms / 100,000粒 2.11ms |
| frameDelta() 作成（定常） | 5,000粒 0.086ms / 100,000粒 1.48ms |
| Canvas 2D 全点描画（ブラウザ実測） | 5,000粒 1.5ms / 50,000粒 21ms / 200,000粒 85ms / 600,000粒 281ms（1フレーム） |

差分検出・統計・描画はいずれも全粒子走査だが、現行規模
（〜5,000粒）では物理計算に対して小さい。支配項は活動粒子の
表面評価を含む接触探索であり、休止・スケジューラ・領域共有の
いずれでも消えない。

## 描画差分転送の比較（5,000粒・30フレーム実測）

| 条件 | 全量 snapshot | 差分転送 |
|---|---|---|
| 弱い駆動 | 1,199,888 B | 644,104 B（約 46% 減） |
| 強い駆動 | 1,183,296 B | 1,352,880 B（約 14% 増） |

強駆動では変化する粒子が多く、番号（4B/粒）の分だけ増える。
条件付きで全量へ切り替える方式は、表示側に「番号なし全量」の
別経路が要り、得られる削減は最悪ケースで 14% 程度、CPU 時間は
同程度（どちらも全粒子走査）であるため、今回は採用しない。
差分方式の利点は、模様が形成された状態（鑑賞の主場面）で
転送と確保が減ることとして記録する。

## メモリ

粒子あたりの配列は概算で約 110 バイト（状態 54 + 休止管理 25 +
スケジューラ 8 + 差分転送 17、その他）。60万粒で約 66MB。
領域表は約 1.2MB（64×64×18自由度×2）で粒子数に依存しない。

## テスト結果（M6-3R 最終）

- Python: 75 件合格（参照実装は無変更。物理の意味は変えていない）
- Web: 41 件合格、ビルド成功（監査テスト 7 件を追加）
- ブラウザ（Chrome headless、実ビルド）: Sand 演奏モードで再生し、
  物理時刻 0→1.7 秒の進行、休止 69% 表示、砂の描画を確認。
  Plate / Fluid タブも表示・操作に回帰なし（ページエラーなし）。
  音声は headless のため聞き取り未確認（従来どおり）。
  本番相当の実機（スマートフォン）確認は未実施。

## 残っているボトルネック

1. 活動粒子の板表面評価（surfAt）が支配的。粒子ごとに毎ステップ
   複数回評価しており、休止でもスケジューラでも消えない。
2. 強い駆動では大半の粒子が活動し続け、休止・領域共有の利益が薄い。
3. Canvas 2D の全点描画は 60万粒で約 281ms/フレームとなり、
   そのままでは実用的でない。
4. stats / 差分検出の全粒子走査（100,000粒で各 ~1ms 級）。

## 60万粒リアルタイムへの見通し

現構造のままでは届かない。100,000粒・弱駆動で物理 0.2 秒に
約 89〜93 秒（物理1秒あたり約 460 秒相当）かかり、60万粒では
その約6倍になる。必要なのは管理の削減ではなく表面評価そのものの
削減・並列化である。粒子同士が独立という現在のモデルでは、
粒子集合を複数 Worker へ分割しても物理は変わらない（板は共有の
先読み結果を配れる）ため、並列化は物理を変えずに効く候補である。
GPU 計算も候補だが、結果の検証方式を別途用意する必要がある。

## M6-4 で取り組むべきこと

- 粒子集合の複数 Worker 分割（独立粒子モデルの範囲で厳密に並列化）
- 表面評価のバッチ化（複数粒子の同一時刻評価をまとめる）
- セル粒度と先読み窓の調整による領域判定の当たり率改善（実測で選ぶ）
- 大規模表示の方式選定（Canvas 2D の限界測定済み、WebGL 等の検討）
- 60万粒の短時間実測と、事前計算動画との役割分担の整理

## 最終判定（M6-3R）

**MERGE-READY**

根拠: 物理的な正しさに関する新しい問題は監査で見つからなかった。
スケジューラと領域共有は境界条件を含む検証を通過し、差分転送の
再構成は全量 snapshot と一致する。性能は反復計測により
「M6-2 と概ね互角〜弱駆動で改善、強駆動の大規模では領域共有に
数% の追加コストがあり得る」と確定した。残課題は上記のとおり
M6-4 の対象として整理した。
