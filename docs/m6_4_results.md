# M6-4 板表面計算の高速化・粒子並列計算・大規模描画の結果

設計は `docs/m6_4_design.md`。物理モデル・休止保証は変更していない。
計測環境: Intel Core i9-10910 / 32GB / Node v22.22.2（Node計測）と
Chrome headless（ブラウザ計測）。物理条件は152Hz・seed 7で統一。

## 4A 板表面評価 surfAt の高速化【採用】

旧 surfAt は呼び出しごとに、時刻だけの関数である Hermite 係数を
自由度ごとに再計算し、配列を2つ確保していた。最適化版は

- 時刻係数（自由度ごとの q/qd/qdd）を正確な時刻をキーに共有
- 漸化用配列を再利用スクラッチへ、R と dR/a を平坦化した表へ

演算式と合計順序は同一で、最適化版と参照版（保持した
`surfAtReference`）の出力はビット一致（原点・外周・ビン境界・
周波数変更直後を含むテストで固定）。全体の衝突・離脱回数も
従来値と一致した。

実測（同一プロセスで参照版へ差し替えて交互実行、中央値）:

| 条件（物理0.5秒） | 参照版 | 最適化版 | 短縮 |
|---|---|---|---|
| 5,000粒・強・休止OFF | 17.29s | 11.17s | 約35% |
| 5,000粒・強・休止ON | 17.60s | 11.09s | 約37% |
| 5,000粒・弱・休止ON | 15.15s | 9.44s | 約38% |

不採用: 着座粒子の空間重みの粒子ごとキャッシュ。メモリが
粒子あたり自由度×3×8B（60万粒で約260MB）に達し、大規模化と
逆行するため。時刻を丸める方式も、結果が変わるため不採用。

## 4B 複数 Worker 並列計算【採用】

方式: 各 Worker が板を複製し（決定的・粒子非依存、コストは
物理1秒あたり約0.1秒）、粒子集合を連続分割する。板状態の配布方式は
毎ステップ通信が必要なため不採用。

- 同一 (count, seed) から全粒子を生成してから分割するため、
  1 Worker の場合と初期粒子群・ID が一致する。
- 調整役が全 Worker へ同一ステップ数のバッチを送り、全シャードの
  同一物理時刻フレームが揃ってから表示する。制御変更はバッチ
  境界で一斉適用される。世代番号で再初期化前の遅延フレームを捨てる。
- プロセス内再現では、分割統合結果が単一計算とビット一致
  （位置・速度・状態・回数、周波数変更を挟んでも一致）。
- ブラウザ実測（5,000粒・実時間9秒で進んだ物理時刻）:
  1 Worker 0.3秒 / 2 Worker 0.8秒 / 4 Worker 1.7秒 / 8 Worker 2.5秒。
- プロセス内シャード計測（逐次実行、最遅シャード＝理想並列の見積り）:
  100,000粒 K=4 で理想約3.9倍、600,000粒 K=8 で理想約7.4倍。
  衝突回数の合計は単一計算と一致。
- 既定の Worker 数は「コア数−1、最大4」。URL の `?workers=N` で
  上書きできる（計測用）。SharedArrayBuffer は使わない。

限界: バッチ完了待ちのため、最遅シャードが全体の速度を決める。
シャード間の負荷は着座・活動の偏りで変わり得る（今回は概ね均等）。

## 4C 大規模描画（WebGL）【採用】

- WebGL の点描画。座標は粒子番号順バッファ、消失粒子は頂点
  シェーダで描画範囲外へ送る（水増しなし）。投影・色・点サイズは
  Canvas 2D と同一。
- バッファ更新は差分フレームの変更範囲のみ（広い場合は全量）。
- WebGL 不可・コンテキスト喪失時は Canvas 2D へ自動で戻る
  （`?gl=0` で強制も可能）。統合表示は両経路で同じ見た目を
  スクリーンショットで確認した。

描画単体ベンチ（物理停止・既知座標、ブラウザ実測）:

| 粒子数 | Canvas 2D | WebGL 全量+描画 | WebGL 差分10%+描画 |
|---|---|---|---|
| 5,000 | 1.52ms | 0.07ms | 〜0ms |
| 50,000 | 21.3ms | 0.23ms | 0.02ms |
| 100,000 | （未計測・線形外挿で約43ms） | 3.55ms | 0.17ms |
| 200,000 | 85.1ms | 1.63ms | 0.03ms |
| 600,000 | 281ms | 3.5〜9.9ms | 0.34ms |

WebGL の数値は GPU 完了待ち（finish）を含む条件でも同程度で、
実際に画素が描かれていることを読み戻しで確認した。描画は
60万粒でもボトルネックではなくなった。

## 4D 統合実測（単一計算、4A適用後）

| 条件 | 実測 | 物理1秒あたり |
|---|---|---|
| 20,000粒・強 (0.2s) | 18.7s | 約94秒 |
| 100,000粒・弱 (0.2s) | 70.8s | 約354秒 |
| 600,000粒・弱 (0.05s) | 67.4s | 約1,349秒 |

表面評価回数は 20,000粒・強で物理1秒あたり約2.69億回。
600,000粒の初期0.05秒は落下・衝突が集中する最も重い区間であり、
定常状態の単価ではない。メモリは 600,000粒で RSS 約203MB
（計測プロセス全体）。

## 60万粒の見通し（実測と推定を区別する）

- 実測: 600,000粒・弱駆動の初期0.05秒は単一計算で67.4秒、
  8分割の最遅シャードは7.9秒だった。
- 推定: 8 Worker 並列が理想どおり効いても、弱駆動の初期区間で
  物理1秒あたり約160秒、定常化しても桁は変わらない。
  リアルタイム（×1）には約2桁の改善がさらに必要である。
- 描画は WebGL で 60万粒でも約10ms/フレーム以下となり、
  律速は物理計算側に一本化された。

## テスト結果

- Python: 75件合格（参照実装は無変更）
- Web: 44件合格、ビルド成功。追加: surfAt 最適化版＝参照版の
  ビット一致、分割統合＝単一計算のビット一致（K=2,3,4）
- ブラウザ: Worker数1/2/4/8の進行速度、WebGL/Canvas2D 両経路の
  表示一致、Plate/Fluid 回帰なしを確認。音の聞き取りと
  スマートフォン実機は未確認（従来どおり）。

## 残っている最大のボトルネック

活動粒子の表面評価を含む接触探索そのもの。4A で約35%速くなり、
4B でコア数近くまで並列化できるようになったが、粒子ステップ
あたり約2回の表面評価という構造は変わっていない。

## 次の段階への提案

1. 表面評価のバッチ化の深化（同一時刻サンプルの一括評価、
   接触探索のサンプル数適応化は保証範囲の再検証が前提）
2. シャード間の負荷平準化（活動率に応じた動的再分割は
   粒子 ID と履歴の扱いを要設計）
3. GPU 計算（WebGPU 等）は、CPU 参照との一致検証方式を
   先に設計してから
4. 事前計算動画との役割分担（60万粒の「鑑賞」は配信、
   「計算」は対話可能な規模に、という整理）
