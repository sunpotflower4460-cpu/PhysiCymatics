# M6-1D 処理時間の内訳（実測）

計測環境: 開発機（macOS）。Python = `scripts/profile_m6.py`、
TS = Node/vitest 上のベンチ（ブラウザ実測とは別。条件: 152Hz・較正力・0.2秒）。

## 内訳

| 処理 | Python実測 | TS実測 | 粒子数依存 |
|---|---|---|---|
| 板モード時間発展 | 797µs/step（1338 stepで1.07s） | 1338 stepで62ms（46µs/step） | なし |
| 表面評価 surf_at | 6.1µs/粒子（5000粒バッチ） | 1.5µs/call（1粒子） | 比例 |
| 砂ステップ全体（500粒・0.2s） | 80.5s | 最適化前 4.13s → 上限skip後 **0.97s** | 比例 |
| 同（2,000粒） | 92.0s | 17.4s → **3.98s** | 比例 |
| 同（5,000粒） | 285.8s | 49.2s → **8.25s** | 比例 |
| snapshotコピー | 0.03〜0.09ms | 0.8〜2.4ms | 比例（小さい） |
| 統計（中央値ソート等） | snapshot内包 | snapshot 1回に含む | 比例（小さい） |

Python参照実装は正確さ優先で非常に遅い（イベント探索の呼び出し回数が支配的）。
高速化の主経路はTS側であり、Pythonは数値の審判として使う。

## 分かったこと

1. **最も時間を使うのは表面評価の繰り返し**（接触探索のサンプル＋二分探索）。
   1粒子・1ステップで最大で数十回呼ばれる。
2. 粒子数に比例するのは表面評価・飛行更新・衝突探索・着座更新・コピー。
   板のモード発展だけが粒子数に無関係。
3. **毎ステップ計算しなくてよいもの**（物理条件から判断可能）:
   - 板面の上限より十分高い飛行粒子（今回の保守的上限skipで実証。結果不変で約4倍）。
   - `g+wtt>=0` が保証できる着座粒子（設計: `docs/m6_2_event_driven_design.md`）。
   - 着座割合は今回条件で約6〜8%と低かったが、形成が進んだ長時間条件では
     上がる見込み（M1の24秒実行では着座が支配的になる時間帯がある）。

## 修正前後の速度（正直な記録）

イベント正確化により、最適化前はTSで約5倍遅くなった（500粒: 旧 約0.25x → 0.05x）。
保守的上限skip（物理結果は不変、照合済み）を入れて 0.21x まで回復した。
Pythonは旧実装より大幅に遅いままである（審判用途に限定）。
